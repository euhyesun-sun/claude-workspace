# Linkaidata Report Platform - 보고서 개발 가이드 (v2)

> 본 문서는 Linkaidata Report Platform에 등록할 Next.js 보고서를 개발할 때 준수해야 할 규칙과 가이드를 정의합니다.
> **v2는 현재 플랫폼 구현(Next.js 15.5 / Node.js 22, 게이트웨이 자동 경로 보정)에 맞춰 갱신되었습니다.** 이전 판(v1.7)과의 주요 차이는 문서 하단 [변경 이력](#변경-이력)을 참고하세요.

---

## 0. v1 → v2 핵심 요약 (먼저 읽기)

기존에 보고서를 개발해 본 적이 있다면, 아래 세 가지가 가장 크게 바뀌었습니다.

| 항목 | v1(과거) | v2(현재) |
|------|----------|----------|
| **클라이언트 `fetch('/api/...')`** | 개발자가 `appUrl()` 헬퍼로 직접 보정 **필수** | 플랫폼 게이트웨이가 **자동 보정**(HTML에 fetch/XHR 패치 주입 + 미들웨어 Referer 폴백). `appUrl()`은 이제 **권장(방어적)** 수준 ([5.5절](#55-standalone-하위-경로basepath-서빙-규칙)) |
| **사용자 정보 연동** | 보고서에 프록시 API 작성 + `initPlatformToken()`으로 토큰을 쿠키에 저장 후 리로드 | 보고서가 같은 오리진(`/r/{id}`)으로 서빙되므로 **`fetch('/api/platform/user-info')`를 그대로 호출**하면 세션 쿠키로 인증됨. 프록시·토큰 리로드 **불필요** ([4장](#4-플랫폼-사용자-정보-연동-선택)) |
| **`node_modules` 포함** | ZIP에서 제외 "권장" | 포함 시 **빌드 즉시 실패**(하드 차단). 반드시 제외 ([2.3절](#23-zip에-포함하면-빌드가-실패하거나-거부되는-것)) |

> ⚠️ v1 방식(프록시 API, `initPlatformToken`, `appUrl`)으로 만든 보고서도 **그대로 동작**합니다. v2는 더 간단한 길을 새로 열었을 뿐이며, 기존 패턴을 강제로 걷어낼 필요는 없습니다.

## 1. 개요

### 1.1 보고서란?
플랫폼에 ZIP 파일로 업로드되는 Next.js 웹 애플리케이션입니다. 업로드 후 자동으로 빌드되어 Private URL(로그인·권한 필요) 또는 Public URL(공개링크 토큰)로 접근할 수 있습니다.

### 1.2 빌드 방식
플랫폼은 두 가지 빌드 전략을 자동으로 시도합니다:

| 빌드 모드 | 설명 | 적용 조건 |
|-----------|------|-----------|
| **Static Export** | 정적 HTML로 빌드 (`output: 'export'`) | API 라우트가 없고 정적 페이지만 있는 경우 |
| **Standalone** | Next.js 서버로 실행 (`output: 'standalone'`) | API 라우트, 서버 컴포넌트, 동적 데이터가 있는 경우 |

> 정적 빌드가 먼저 시도되고, 실패 시 자동으로 standalone 모드로 전환됩니다.

### 1.3 빌드 시 자동 처리 항목
플랫폼이 빌드 과정에서 자동으로 처리하는 항목입니다. 개발자가 직접 설정할 필요 없습니다.

- `next.config.js`의 `output` 설정 (자동 주입)
- `typescript.ignoreBuildErrors: true` (타입 에러 무시)
- `eslint.ignoreDuringBuilds: true` (린트 에러 무시)
- `images.unoptimized: true` (이미지 최적화 비활성화)
- `experimental.outputFileTracingRoot` (업로드 프로젝트 루트로 고정 — standalone 출력에 빌드 임시 경로가 중첩되는 문제 방지, 자동 주입)
- `trailingSlash: true` (**Static Export 전용** — standalone에는 적용되지 않음)
- `basePath: '/r/{보고서ID}'` (**Standalone 전용** — 하위 경로 서빙, [5.5절](#55-standalone-하위-경로basepath-서빙-규칙) 필독)

> **참고:** 의존성 설치는 `npm install --legacy-peer-deps`로 수행됩니다. 따라서 React 19 등에서 흔한 peer dependency 충돌이 있어도 설치가 중단되지 않습니다.

## 2. 디렉토리 구조

### 2.1 필수 구조

```
my-report/
├── package.json          # [필수] 프로젝트 의존성 정의
├── src/                  # 또는 루트에 app/ 디렉토리
│   └── app/
│       ├── layout.tsx    # [필수] 루트 레이아웃
│       ├── page.tsx      # [필수] 메인 페이지
│       └── api/          # [선택] API 라우트 (standalone 빌드가 됨)
│           └── data/
│               └── route.ts
├── public/               # [선택] 정적 파일 (이미지, 폰트 등)
├── .env.local            # [선택] 환경변수 (개발용, ZIP에 포함 가능)
├── tsconfig.json         # [권장] TypeScript 설정
└── next.config.js        # [선택] 플랫폼이 자동 덮어쓰기함
```

> **사용자 정보 연동용 프록시 API(`api/platform/user-info/route.ts`)는 v2에서 더 이상 만들 필요가 없습니다.** 자세한 내용은 [4장](#4-플랫폼-사용자-정보-연동-선택) 참고.

### 2.2 ZIP 패키징 규칙

```
my-report.zip
├── my-report/            # 프로젝트 폴더 (중첩 허용)
│   ├── package.json
│   ├── src/
│   └── ...
```

- ZIP 루트에 `package.json`이 있거나, **1~3단계 하위 폴더**에 있어야 합니다 (더 깊으면 "No package.json found")
- 최대 파일 크기: **200MB**
- 파일 형식: `.zip`만 허용
- ZIP 내 최대 엔트리 수: **20,000개** (초과 시 빌드 거부 — 불필요한 파일 포함 여부 점검)

### 2.3 ZIP에 포함하면 빌드가 실패하거나 거부되는 것

| 제외 대상 | 결과 |
|-----------|------|
| `node_modules/` | **빌드 즉시 실패** (하드 차단) — 빌드 시 자동 설치되므로 반드시 제외 |
| 엔트리 20,000개 초과 | **빌드 거부** |
| `.next/` | 불필요 (빌드 시 자동 생성) — 크기만 증가 |
| `.git/` | 불필요 |

> **v1과의 차이:** v1에서는 `node_modules` 제외가 "권장"이었으나, v2 빌드 워커는 ZIP을 풀기 전에 `node_modules/` 포함 여부를 검사해 **포함되어 있으면 빌드를 실패시킵니다.** (`"Zip contains node_modules — please exclude node_modules and re-upload"`)

> `.env.production` 등 비밀값이 담긴 파일은 넣지 않는 것을 권장합니다. 환경변수는 플랫폼이 별도 관리합니다([3.3절](#33-환경변수-env)).

## 3. 설정 파일 규칙

### 3.1 package.json (필수)

```json
{
  "name": "my-report",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  },
  "dependencies": {
    "next": "14.x 또는 15.x",
    "react": "^18.0.0 또는 ^19.0.0",
    "react-dom": "^18.0.0 또는 ^19.0.0"
  }
}
```

**필수 사항:**
- `next`, `react`, `react-dom` 의존성이 반드시 포함되어야 합니다
- `build` 스크립트가 정의되어야 합니다

**주의 사항:**
- `next.config.js`의 `output` 설정은 플랫폼이 자동 덮어쓰므로 직접 설정하지 않아도 됩니다
- 빌드 타임아웃: **npm install 3분, next build 3분** (모드별로 static → standalone 순차 시도 시 각 build가 3분)

### 3.2 next.config.js (선택)

> 플랫폼이 빌드 시 `next.config.js`를 **완전히 새로 작성해 덮어씁니다.** 아래 설정만 보장되며, 그 외 커스텀 설정은 적용되지 않습니다.

플랫폼이 주입하는 설정:
```javascript
// Static Export 시
const nextConfig = {
  output: 'export',
  trailingSlash: true,               // Static 전용
  typescript: { ignoreBuildErrors: true },
  eslint: { ignoreDuringBuilds: true },
  images: { unoptimized: true },
  experimental: { outputFileTracingRoot: '<프로젝트 루트>' },
};

// Standalone 시 (정적 빌드 실패 후 폴백)
const nextConfig = {
  output: 'standalone',
  basePath: '/r/{보고서ID}',          // Standalone 전용 (5.5절 참고)
  typescript: { ignoreBuildErrors: true },
  eslint: { ignoreDuringBuilds: true },
  images: { unoptimized: true },
  experimental: { outputFileTracingRoot: '<프로젝트 루트>' },
};
```

> **중요:** `next.config.js`에 webpack 커스텀 설정, `rewrites`, `headers`, `redirects` 등이 필요한 경우 현재는 플랫폼이 덮어쓰므로 적용되지 않습니다.

### 3.3 환경변수 (.env)

보고서별 환경변수는 플랫폼의 **보고서 디렉토리**에 `.env` 파일로 관리됩니다. (웹 UI에서 편집 가능 — [11.2절](#112-환경변수-웹-ui-관리))

**플랫폼이 자동 주입하는 환경변수 (standalone 실행 시):**

| 변수명 | 설명 | 예시 |
|--------|------|------|
| `PORT` | 보고서 서버 포트 (14000~14999 범위에서 동적 할당) | `14001` |
| `HOSTNAME` | 바인딩 호스트 (외부 직접 접근 불가) | `127.0.0.1` |
| `NODE_ENV` | 실행 환경 | `production` |
| `PLATFORM_URL` | 플랫폼 API 주소(요청이 도달한 실제 외부 오리진) | `http://localhost:3000` |

> **참고:** `platform_token`은 환경변수로 주입되지 않으며, v2에서는 URL로도 전달하지 않습니다. 로그인 사용자 인증은 같은 오리진의 세션 쿠키로 처리됩니다([4장](#4-플랫폼-사용자-정보-연동-선택)).

**보고서별 커스텀 환경변수:**

보고서 디렉토리의 `.env` 파일에 정의합니다 (웹 UI 또는 서버에서 설정).

```env
# 예: DB 모니터링 보고서
DB_LIST=PROD_MAIN,OCRA
DB_PROD_MAIN_HOST=192.168.1.100
DB_PROD_MAIN_PORT=5432
DB_PROD_MAIN_DBNAME=mydb
DB_PROD_MAIN_USER=readonly
DB_PROD_MAIN_PASSWORD=secret
```

> - `.env` 파일은 빌드 시와 실행 시 **모두** 적용됩니다.
> - 최초 빌드 시 관리용 `.env`가 없고 ZIP 안에 `.env`가 있으면 **1회 시딩**됩니다. 이후에는 웹 UI에서 편집한 관리용 `.env`가 항상 우선하며, ZIP의 `.env`로 덮어써지지 않습니다.

## 4. 플랫폼 사용자 정보 연동 (선택)

> **이 기능은 필수가 아닙니다.** 로그인 사용자별 정보(이름, 그룹, 권한 등)가 필요한 경우에만 사용합니다. 정적 대시보드·DB 조회 보고서 등은 이 장을 건너뛰어도 됩니다.

### 4.1 v2에서 달라진 점 (가장 중요)

보고서는 플랫폼과 **같은 오리진**(`http://플랫폼주소/r/{보고서ID}`)의 게이트웨이를 통해 서빙됩니다.
따라서 보고서 클라이언트에서 플랫폼 API를 **그대로 호출**하면 브라우저가 플랫폼의 세션 쿠키를 함께 전송하고, 플랫폼이 로그인 사용자를 식별합니다.

```typescript
// ✅ v2 — 이것이 전부입니다. 프록시·토큰·리로드 불필요.
const res = await fetch('/api/platform/user-info');
const json = await res.json();
if (json.success) {
  console.log(json.data.name, json.data.groups);
}
```

- `/api/platform/*` 경로는 **플랫폼 전용 네임스페이스**입니다. 게이트웨이의 자동 경로 보정(5.5절)에서도 이 경로만은 보고서 하위로 재작성하지 않고 **플랫폼 루트로 그대로 보냅니다.**
- 따라서 **보고서 안에 `api/platform/user-info` 프록시 라우트를 직접 만들지 마세요.** 만들어도 위 경로 호출은 플랫폼으로 가므로 그 라우트에는 도달하지 않습니다.
- v1의 `initPlatformToken()`(URL 토큰 → 쿠키 저장 → 리로드) 절차도 **더 이상 필요 없습니다.** "열기"는 이제 URL로 `platform_token`을 전달하지 않으며(오직 `platform_url`만 전달), 인증은 세션 쿠키가 담당합니다.

### 4.2 제공 데이터 / 응답 형식

**API:** `GET /api/platform/user-info` (플랫폼이 직접 제공, 같은 오리진)

```json
{
  "success": true,
  "data": {
    "id": "uuid-string",
    "username": "admin",
    "name": "관리자",
    "email": "admin@mobigen.com",
    "role": "ADMIN",
    "groups": [
      {
        "id": "uuid-string",
        "name": "관리그룹",
        "description": "시스템 관리자 그룹",
        "role": "MEMBER"
      }
    ]
  }
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| `id` | string (UUID) | 사용자 고유 ID |
| `username` | string | 로그인 아이디 |
| `name` | string | 사용자 이름 |
| `email` | string | 이메일 |
| `role` | string | 역할 (ADMIN / USER) |
| `groups` | array | 소속 그룹 목록 (`id`, `name`, `description`, `role`) |

> 인증되지 않은 요청에는 `401 { success: false, error: "Not authenticated" }`를 반환합니다.

### 4.3 클라이언트 구현 예시

```typescript
'use client';
import { useState, useEffect } from 'react';

interface Group { id: string; name: string; description: string | null; role: string; }
interface PlatformUser { id: string; username: string; name: string; email: string; role: string; groups: Group[]; }

export default function Dashboard() {
  const [user, setUser] = useState<PlatformUser | null>(null);

  useEffect(() => {
    // 같은 오리진(/r/{id})이므로 세션 쿠키가 자동 전송된다.
    fetch('/api/platform/user-info')
      .then((res) => res.json())
      .then((json) => {
        if (json.success && json.data) setUser(json.data);
      })
      .catch(() => {});
  }, []);

  return <div>{user ? `안녕하세요, ${user.name}님` : '로딩 중...'}</div>;
}
```

> **참고:** `/api/platform/user-info`는 플랫폼 전용 경로라 basePath 보정 대상이 아니므로, 위처럼 **절대경로 그대로** 두는 것이 맞습니다. (보고서 자신의 API 호출은 5.5절 참고.)

### 4.4 (레거시) 프록시 API 방식

> v1에서 만든 보고서와의 호환을 위해 남겨둡니다. **신규 개발에서는 4.3을 사용하세요.**

과거에는 보고서에 서버사이드 프록시 API를 두고, 클라이언트가 URL의 `platform_token`을 쿠키에 저장한 뒤 그 토큰을 프록시가 플랫폼으로 전달했습니다. 이 방식은 지금도 동작하지만(플랫폼의 `resolveUserId`가 Bearer/`?token=`/`platform_token` 쿠키를 모두 지원), v2에서는 "열기"가 URL 토큰을 발급하지 않으므로 세션 쿠키를 쓰는 4.3 방식이 더 단순하고 안전합니다.

### 4.5 SDK 사용 (대안 — 크로스 도메인 임베딩용)

보고서를 **플랫폼과 다른 도메인**에 두고 iframe 등으로 임베딩할 때는 SDK를 사용할 수 있습니다.

```html
<script src="http://[플랫폼주소]/sdk/linkaidata-platform.js"></script>
<script>
  LinkaidataPlatform.getUserInfo().then(function (user) {
    console.log(user.name, user.groups);
  });
</script>
```

- SDK는 `credentials: 'include'`로 요청하므로 같은 사이트에서는 세션 쿠키로 인증됩니다.
- 크로스 도메인에서 credentials 요청을 허용하려면 플랫폼 관리자가 `SDK_ALLOWED_ORIGINS` 환경변수에 보고서 오리진을 등록해야 합니다(임의 오리진은 CORS로 차단).
- iframe 임베딩 시 부모(플랫폼)로부터 `postMessage`(`LINKAIDATA_USER_INFO`)로 사용자 정보를 받을 수도 있습니다(`LinkaidataPlatform.onUserInfo(cb)`).

> 같은 오리진(`/r/{id}` 게이트웨이)으로 서빙되는 일반 보고서는 SDK 없이 [4.3](#43-클라이언트-구현-예시)의 직접 호출을 **권장**합니다.

### 5.2 정적 빌드 호환 (Static Export)

정적 빌드로 성공하려면 다음을 준수해야 합니다:

- API 라우트(`/api/*`)를 사용하지 않아야 합니다
- `export const dynamic = 'force-dynamic'`을 사용하지 않아야 합니다
- 서버 컴포넌트에서 동적 데이터 페칭을 하지 않아야 합니다
- `getServerSideProps`를 사용하지 않아야 합니다

> 위 조건을 충족하지 않으면 자동으로 standalone 모드로 빌드됩니다.

### 5.3 Standalone 빌드 호환

Standalone 모드로 빌드되는 경우:

- API 라우트 사용 가능
- 서버 컴포넌트 / 동적 데이터 페칭 가능
- 보고서별 독립 포트(**14000~14999**, `127.0.0.1` 바인딩)에서 실행되며, 브라우저는 직접 접속하지 않고 플랫폼 게이트웨이(`/r/{보고서ID}`, 포트 3000)를 통해서만 접근합니다 ([5.5절](#55-standalone-하위-경로basepath-서빙-규칙) 필독)
- **콜드 스타트:** 서버가 꺼져 있을 때 처음 열면 게이트웨이가 즉시 **로딩 페이지**(스피너)를 반환하고 백그라운드로 서버를 기동합니다. 준비되면(약 30초 내) 자동으로 새로고침되어 보고서가 표시됩니다.
- 일정 시간 유휴 시 자동 종료(기본 10분), 재접속 시 자동 재시작
- 동시 실행 서버 수에 상한이 있어(기본 10개), 초과 시 가장 오래 미사용된(LRU) 서버부터 종료됨

| 설정 | 환경변수 | 기본값 |
|------|----------|--------|
| 유휴 종료 시간 | `REPORT_IDLE_TIMEOUT_MS` | `600000` (10분) |
| 동시 실행 서버 수 상한 | `MAX_REPORT_SERVERS` | `10` |

> 위 값은 플랫폼 관리자가 서버 환경변수에서 조정합니다. 보고서 개발자는 신경 쓸 필요 없으나, 유휴 종료·재시작이 일어나므로 보고서는 **상태를 서버 메모리에만 보관하지 말고** 매 요청이 독립적으로 동작하도록 작성하는 것이 안전합니다.

### 5.4 빌드 제약 사항

### 5.5 Standalone 하위 경로(basePath) 서빙 규칙

> **배경**: standalone 보고서는 `/r/{보고서ID}` 하위 경로로 서빙됩니다. 과거 클라이언트의
> `fetch('/api/...')` 절대경로 호출이 보고서가 아닌 **플랫폼 루트**로 전송되어 실패하는
> 문제가 있었고, v2에서는 플랫폼이 이를 **자동 보정**합니다.

빌드 시 `basePath: '/r/{보고서ID}'`가 자동 주입됩니다.

**basePath가 자동 처리해주는 것 (개발자가 신경 쓸 필요 없음):**

| 항목 | 동작 |
|------|------|
| `<Link href="/page">` | `/r/{id}/page`로 자동 변환 |
| `router.push('/page')` | `/r/{id}/page`로 자동 이동 |
| 서버 컴포넌트의 `redirect('/login')` | `Location: /r/{id}/login`으로 자동 변환 |
| 정적 자산(`/_next/...`) | `/r/{id}/_next/...`로 자동 참조 |

**v2에서 플랫폼이 추가로 자동 보정해주는 것:**

플랫폼 게이트웨이는 보고서 HTML 응답에 **fetch/XHR 패치 스크립트**를 주입하고, 미들웨어에서 **Referer 기반 폴백 재작성**을 수행합니다. 그 결과:

| 항목 | v2 동작 |
|------|---------|
| `fetch('/api/data')` (보고서 자신의 API) | 주입된 shim이 `/r/{id}/api/data`로 자동 재작성 → 정상 도달 |
| shim이 놓친 경우 | 미들웨어가 Referer(`/r/{id}/...`)를 보고 보고서 게이트웨이로 재작성 |
| `/api/platform/*`, `/api/auth`, `/api/public` 등 | **플랫폼 전용 경로**로 인식하여 보고서로 재작성하지 않음(플랫폼 루트로 전달) |

> **결론:** v2에서는 대부분의 보고서가 `fetch('/api/...')`를 그대로 써도 동작합니다.
> 다만 자동 보정은 **HTML 주입/Referer에 의존**하므로 다음 경우엔 여전히 실패할 수 있습니다:
> Web Worker/Service Worker 내부 fetch, HTML로 주입되지 않는 응답, Referer를 축약하는 일부 브라우저(Safari ITP) 등.
> 따라서 아래 `appUrl()` 헬퍼는 **여전히 권장(방어적 사용)**합니다.

#### REPORT-PATH-001 · (권장) 클라이언트 자체 API 호출에 basePath 헬퍼를 사용한다

✅ **권장 패턴** — basePath 헬퍼를 만들어 사용한다.

**파일:** `src/lib/app-url.ts`

```typescript
/**
 * standalone 보고서는 /r/{보고서ID} 하위 경로로 서빙된다.
 * 클라이언트에서 자체 API 호출·페이지 이동 시 이 헬퍼를 사용하면
 * 로컬 개발(루트 서빙)과 플랫폼 배포(/r/{id} 서빙) 양쪽에서 모두 동작한다.
 */
export function getBasePath(): string {
  if (typeof window === 'undefined') return '';
  const m = window.location.pathname.match(/^\/r\/[^/]+/);
  return m ? m[0] : '';
}

/** 앱 내부 절대 경로('/api/...', '/', '/page')를 실제 요청 경로로 변환 */
export function appUrl(path: string): string {
  return `${getBasePath()}${path}` || '/';
}
```

**사용 예:**

```typescript
import { appUrl } from '@/lib/app-url';

// 보고서 자신의 API 호출
const res = await fetch(appUrl('/api/data'));

// 전체 페이지 이동 (Next 라우터를 쓰지 않는 경우)
window.location.assign(appUrl('/login'));
```

> **주의:** 플랫폼 API(`/api/platform/user-info` 등)에는 `appUrl()`을 쓰지 마세요. 해당 경로는 플랫폼 루트로 가야 하므로 **절대경로 그대로** 둡니다([4.3절](#43-클라이언트-구현-예시)).

#### REPORT-PATH-002 · 인증 직후 이동은 `router.push` 대신 전체 이동을 권장

쿠키 기반 인증 직후에는 서버가 새 쿠키로 페이지를 다시 렌더링해야 하므로,
`router.push()` + `router.refresh()` 조합보다 `window.location.assign(appUrl('/'))`
전체 이동이 하위 경로 환경에서 더 안정적으로 동작합니다.

#### 코드 리뷰 체크리스트

- [ ] 보고서 자신의 API 호출에 `appUrl()`을 사용했거나, 자동 보정만으로 충분한지 확인했는가?
- [ ] `/api/platform/*` 등 플랫폼 API는 절대경로 그대로 두었는가?
- [ ] Web Worker/Service Worker 내부에서 `/api/...`를 호출하지 않는가? (자동 보정 미적용)
- [ ] 로컬에서 `/r/test/` 형태의 리버스 프록시로 배포 환경을 재현해 테스트했는가?

### 5.6 Tailwind CSS 사용 규칙 (Linux 빌드 필수)

> **배경**: Windows에서 개발한 보고서를 업로드하자 Linux 빌드 워커에서
> `Error: Cannot find native binding` (`@tailwindcss/oxide`)으로 빌드가 실패한 사례가 있었다.
> 플랫폼 빌드 워커는 **Linux 환경**에서 `npm install → next build`를 수행하므로,
> OS별 네이티브 바이너리에 의존하는 도구는 아래 규칙을 반드시 지켜야 한다.

**핵심**: 보고서는 개발 PC(주로 Windows/macOS)와 **다른 OS(Linux)에서 빌드**됩니다.
따라서 ① OS별 네이티브 바이너리를 요구하는 도구를 피하거나, ② 요구하는 경우
`package-lock.json`을 ZIP에서 제외해 워커가 자기 OS용 바이너리를 직접 받게 해야 합니다.

#### REPORT-CSS-001 · Tailwind CSS는 v3(순수 JS)을 권장한다

Tailwind CSS **v4**는 Rust 기반 네이티브 엔진(`@tailwindcss/oxide`)에 의존합니다.
개발 PC(Windows)에서 만든 `package-lock.json`이 win32 바이너리로 고정되면,
Linux 워커에서 해당 바이너리를 찾지 못해 빌드가 실패합니다.

**권장: Tailwind v3 사용** — 네이티브 바이너리가 없는 순수 JS/PostCSS 구현이라 어떤 OS에서도 안정적으로 빌드됩니다.

✅ **권장 구성 (Tailwind v3)**

**`package.json`** (devDependencies)
```json
{
  "devDependencies": {
    "tailwindcss": "^3.4.17",
    "postcss": "^8.4.49",
    "autoprefixer": "^10.4.20"
  }
}
```

**`postcss.config.mjs`**
```javascript
const config = {
  plugins: {
    tailwindcss: {},
    autoprefixer: {},
  },
};
export default config;
```

**`tailwind.config.ts`** (v3는 config 파일 필수)
```typescript
import type { Config } from "tailwindcss";

const config: Config = {
  darkMode: "class",
  content: ["./src/**/*.{js,ts,jsx,tsx,mdx}"],
  theme: { extend: {} },
  plugins: [],
};
export default config;
```

**`src/app/globals.css`**
```css
@tailwind base;
@tailwind components;
@tailwind utilities;
```

#### REPORT-CSS-002 · v4를 써야 한다면 `package-lock.json`을 ZIP에서 제외해야 한다

> ⚠️ **중요**: Tailwind v4는 아래 조건을 충족하지 않으면 빌드되지 않습니다.
> 별도 설정 없이 확실하게 하려면 REPORT-CSS-001의 **v3 사용을 권장**합니다.

**현재 빌드 워커는 Node 22이므로** Tailwind v4의 Node 버전 요구(`engines: { node: ">= 20" }`)는 이미 충족됩니다. 남은 조건은 아래 하나입니다.

**`package-lock.json`을 ZIP에서 제외** — Windows/macOS에서 생성된 lock은 해당 OS 바이너리를 고정하므로 Linux 워커가 올바른 리눅스 바이너리를 설치하지 못합니다(npm 옵셔널 의존성 버그). lock을 빼면 워커의 `npm install`이 실행 OS에 맞는 바이너리를 새로 받습니다.

| 구성 | 워커 Node | lock | 결과 |
|------|-----------|------|------|
| Tailwind v3 (순수 JS) | 22 | 포함/제외 무관 | ✅ 항상 성공 |
| Tailwind v4 (네이티브) | 22 | Windows/macOS lock 포함 | ❌ `Cannot find native binding` |
| Tailwind v4 (네이티브) | 22 | 제외 | ✅ 워커가 알맞은 바이너리 설치 |

> **참고**: Next.js 자체도 SWC 네이티브 바이너리를 쓰지만 optionalDependencies로 OS별 패키지를 모두 선언하므로, lock을 제외하면 SWC 포함 모든 바이너리가 워커 OS에 맞게 설치됩니다. 즉 "lock 제외"는 네이티브 의존성 전반의 크로스 플랫폼 문제를 예방합니다.

#### v4 → v3 다운그레이드 체크리스트

- [ ] `@tailwindcss/postcss`, `tailwindcss@^4` 제거 → `tailwindcss@^3`, `postcss`, `autoprefixer` 추가
- [ ] `postcss.config`의 플러그인을 `@tailwindcss/postcss` → `tailwindcss` + `autoprefixer`로 변경
- [ ] `tailwind.config.ts` 신규 작성 (`content`, `darkMode` 지정)
- [ ] `globals.css`의 `@import "tailwindcss";` → `@tailwind base/components/utilities;`
- [ ] v4 전용 CSS 문법 제거: `@custom-variant`(→ config `darkMode`), `@theme`(→ config `theme.extend`)
- [ ] 로컬에서 `npm install && npm run build` 재확인

### 5.7 다운로드 파일이 포함된 보고서 규칙 (필독)

> **배경**: `public/`에 첨부파일(zip 등)을 두고 `<a href="파일.zip" download>`로 내려받게 만든
> 보고서를 정적(Static Export)으로 등록하자, 화면은 떴지만 다운로드 클릭 시
> "사이트에서 사용할 수 없는 파일"(404)이 발생한 사례가 있었다. 원인은 아래 두 가지이며,
> **첨부파일 다운로드가 있는 보고서는 반드시 이 절을 지켜야 한다.**

**보고서에 다운로드(첨부)파일이 포함되면, ① standalone으로 빌드되게 하고 ② 다운로드 링크를 basePath 기준으로 처리해야 한다.**

#### REPORT-DL-001 · 다운로드 파일이 있으면 standalone 빌드를 강제한다

정적(Static Export) 보고서는 로그인 사용자가 열 때 플랫폼이 **`index.html` 한 장만** 서빙한다.
`index.html` 바깥의 파일(다운로드용 zip, `public/`의 기타 자산 등)을 내려주는 경로가 없어
그런 파일 요청은 **404**가 된다. 따라서 첨부파일을 제공하는 보고서는 **standalone으로 빌드**되어야
한다. standalone에서는 실제 Next.js 서버가 `public/` 파일을 `/r/{보고서ID}/파일명`으로 서빙하고,
게이트웨이가 이를 프록시하므로 다운로드가 정상 동작한다.

정적 빌드가 먼저 시도되므로([5.2절](#52-정적-빌드-호환-static-export)), standalone으로 유도하려면
정적 export가 실패하도록 **API 라우트를 하나 추가**한다(가장 간단하고 확실한 방법).

**파일:** `src/app/api/health/route.ts`

```typescript
// 정적(export) 빌드를 실패시켜 플랫폼이 standalone 모드로 빌드하도록 유도한다.
// standalone에서만 public/ 첨부파일이 /r/{보고서ID}/ 하위로 서빙된다.
export const dynamic = 'force-dynamic';

export async function GET() {
  return Response.json({ ok: true });
}
```

> 빌드 로그 마지막이 **`Build mode: standalone`**이면 정상이다.
> (`Attempting static export build...` → `Static export failed, falling back to standalone mode...` → `Standalone build succeeded`)

#### REPORT-DL-002 · 다운로드 링크는 basePath 기준 절대경로로 만든다

standalone 보고서의 브라우저 URL은 트레일링 슬래시가 **제거된** `/r/{보고서ID}` 형태다
(메인 앱·보고서 서버가 308로 슬래시를 없앰). 이 상태에서 **상대경로** 다운로드 링크는
마지막 경로 조각(`{보고서ID}`)을 교체하는 방식으로 해석되어 엉뚱한 곳을 가리킨다.

```
현재 URL: /r/{id}          (슬래시 없음)
<a href="file.zip">  →  /r/file.zip   ❌  ({id}가 빠져 게이트웨이가 404)
필요한 경로            →  /r/{id}/file.zip ✅
```

> ⚠️ [5.5절](#55-standalone-하위-경로basepath-서빙-규칙)의 fetch/XHR 자동 보정은
> **일반 `<a>` 이동/다운로드에는 적용되지 않는다**(shim은 `fetch`·`XMLHttpRequest`만 패치).
> 따라서 다운로드 링크 경로는 개발자가 직접 basePath 기준으로 맞춰야 한다.

✅ **권장 패턴** — 렌더 후 클라이언트에서 다운로드 링크의 `href`를 basePath 기준으로 교정한다.
정적 HTML을 그대로 삽입해 원본을 수정하지 못하는 경우에 특히 유용하다.

```typescript
'use client';
import { useEffect } from 'react';

export default function FixDownloadLinks() {
  useEffect(() => {
    // /r/{id} 형태의 하위 경로를 감지 (로컬 개발은 루트 서빙이라 '' → 그대로 동작)
    const basePath = (window.location.pathname.match(/^\/r\/[^/]+/) || [''])[0];
    document.querySelectorAll('a[download]').forEach((a) => {
      const raw = a.getAttribute('href') || '';
      // 절대경로(/…)·외부 URL(http…)·프래그먼트(#…)·data URI는 제외, 상대경로만 교정
      if (raw && !raw.startsWith('/') && !/^[a-z]+:/i.test(raw) && !raw.startsWith('#')) {
        a.setAttribute('href', `${basePath}/${raw}`);
      }
    });
  }, []);
  return null;
}
```

직접 링크를 작성하는 경우에는 [5.5절](#reportpath001--권장-클라이언트-자체-api-호출에-basepath-헬퍼를-사용한다)의
`appUrl()` 헬퍼로 `appUrl('/file.zip')`처럼 basePath를 붙이면 된다.

> **대안:** 첨부파일을 API 라우트(`/api/download/route.ts`)에서 스트리밍으로 내려주면,
> 자체 API 호출은 basePath 자동 보정 대상이라 경로 문제가 발생하지 않는다.
> 다만 이 경우에도 링크가 `<a>` 이동이라면 위 basePath 교정이 필요하다.

#### 코드 리뷰 체크리스트 (다운로드 포함 보고서)

- [ ] `public/`에 다운로드 파일을 두었고, standalone으로 빌드되도록 API 라우트를 넣었는가?
- [ ] 다운로드 링크의 `href`가 `/r/{id}/파일명`으로 해석되는가? (상대경로 그대로 두지 않았는가)
- [ ] 로컬에서 `/r/test`(슬래시 없음) 형태로 서빙해 실제로 다운로드가 200으로 내려오는지 확인했는가?

## 9. 문제 해결 (Troubleshooting)

### 9.1 빌드 실패: "No package.json found"

- ZIP 파일 내에 `package.json`이 3단계 이내에 존재하는지 확인
- ZIP 압축 시 루트에 불필요한 파일이 포함되지 않았는지 확인

### 9.2 빌드 실패: "Zip contains node_modules"

- `node_modules/`를 ZIP에서 제외하고 다시 업로드 (의존성은 빌드 시 자동 설치됨)

### 9.3 빌드 실패: 타임아웃

- 의존성이 지나치게 많거나 무거운 경우 npm install 3분을 초과할 수 있음 — 불필요한 의존성 정리
- ZIP에 불필요한 대용량 파일이 포함되어 있지 않은지 확인

### 9.4 빌드 성공했으나 화면이 비어있음

- Static 빌드로 생성된 경우 API 라우트가 동작하지 않음
- 동적 데이터가 필요한 경우 API 라우트를 사용하여 standalone 빌드가 되도록 유도

### 9.5 환경변수가 적용되지 않음

- 빌드 시점에 필요한 환경변수는 `.env`가 보고서 디렉토리에 있어야 함 (웹 UI로 설정 가능)
- 환경변수 변경 후 **재빌드** 필요 (빌드 시 환경변수가 포함됨)
- 런타임 전용 환경변수는 `process.env.XXX`로 동적 접근해야 함

### 9.6 플랫폼 사용자 정보가 조회되지 않음

- v2에서는 `fetch('/api/platform/user-info')`를 **절대경로 그대로** 호출해야 함 (basePath를 붙이면 안 됨 — 플랫폼 전용 경로)
- 플랫폼에 **로그인된 상태**에서 게이트웨이(`/r/{id}`)로 열었는지 확인 (세션 쿠키로 인증)
- 401이 반환되면 로그인 세션이 없는 것 — 공개링크(비로그인)로 연 경우 사용자 정보가 없을 수 있음
- 보고서 안에 `api/platform/...` 라우트를 직접 만들지 않았는지 확인 (해당 경로 호출은 플랫폼으로 감)

### 9.7 로딩 페이지에서 "Failed to load report"가 표시됨

- standalone 서버가 30초 내에 기동하지 못한 경우 — `server.js` 실행 오류일 가능성
- 보고서 상세의 빌드 로그, 서버 콘솔 로그를 확인
- "Try again" 버튼으로 재시도

### 9.8 API 호출이 404 / "Unauthorized" 등 플랫폼 응답을 받음

**증상**: 보고서 화면은 뜨는데 일부 API 호출이 실패하고, 응답이 보고서 자신의 API 형식이 아닌 플랫폼 응답으로 보임.

**원인**: 자동 보정(shim/미들웨어)이 닿지 않는 경로에서 `fetch('/api/...')`가 플랫폼 루트로 전송됨 (예: Web Worker 내부, HTML 주입이 없는 컨텍스트).

**해결**: 해당 호출에 5.5절의 `appUrl()` 헬퍼를 적용해 `/r/{id}` 경로로 명시적으로 보정한다.

### 9.9 DB 연결 실패

- 환경변수가 보고서 디렉토리의 `.env`에 정확히 설정되어 있는지 확인
- 환경변수 변경 후 재빌드 필요
- 네트워크 접근이 가능한지 확인 (방화벽, VPN 등)

### 9.10 빌드 실패: "Cannot find native binding" (Tailwind CSS 등)

**증상**: 빌드 로그에 아래와 같은 오류가 나오며 컴파일이 실패함.

```
Error: Cannot find native binding. npm has a bug related to optional dependencies
    at Object.<anonymous> (.../node_modules/@tailwindcss/oxide/index.js)
```

**원인**: Tailwind v4 등 OS별 네이티브 바이너리를 요구하는 패키지를 쓰면서, 개발 PC(Windows/macOS)에서 생성한 `package-lock.json`을 ZIP에 포함한 경우.

**해결** (둘 중 하나):
1. **Tailwind v3로 전환** (권장, 네이티브 바이너리 없음) — [5.6절 REPORT-CSS-001](#reportcss001--tailwind-css는-v3순수-js을-권장한다)
2. **`package-lock.json`을 ZIP에서 제외** 후 재업로드 — [5.6절 REPORT-CSS-002](#reportcss002--v4를-써야-한다면-package-lockjson을-zip에서-제외해야-한다)

### 9.11 "legacy (separate-port) method" 409 오류

**증상**: 게이트웨이가 `"This report was built with the legacy (separate-port) method. Please rebuild the report and try again."` 반환.

**원인**: basePath가 박히지 않은 구버전 빌드 산출물.

**해결**: 보고서를 **재빌드**한다 (basePath가 주입된 새 방식으로 다시 생성됨).

### 9.12 첨부파일 다운로드가 "사이트에서 사용할 수 없는 파일"/404로 실패

**증상**: 보고서 화면은 정상인데, 첨부파일 다운로드 링크를 누르면 404 또는 브라우저가
"사이트에서 사용할 수 없는 파일"로 표시한다.

**원인 A — 정적(Static)으로 빌드됨**: 정적 보고서는 `index.html`만 서빙되어 첨부파일 경로가 없다.
→ [5.7절 REPORT-DL-001](#reportdl001--다운로드-파일이-있으면-standalone-빌드를-강제한다)대로 API 라우트를 추가해 **standalone으로 빌드**되게 한다. (빌드 로그 마지막이 `Build mode: standalone`인지 확인)

**원인 B — 상대경로 링크가 하위 경로에서 잘못 해석됨**: standalone인데도 링크가 상대경로라
`/r/{id}` 대신 `/r/파일명`으로 요청되어 404. → [5.7절 REPORT-DL-002](#reportdl002--다운로드-링크는-basepath-기준-절대경로로-만든다)대로 링크를 basePath 기준(`/r/{id}/파일명`)으로 교정한다.

> 확인법: 브라우저 개발자도구 Network 탭에서 다운로드 요청 URL이 `/r/{보고서ID}/파일명`으로
> 나가는지 본다. `/r/파일명`처럼 보고서ID가 빠져 있으면 원인 B다.

## 11. 운영 팁

### 11.1 네트워크 접속 (다른 PC에서 테스트)

개발 시 동일 네트워크 내 다른 PC에서 접속하려면 `0.0.0.0`으로 바인딩하여 실행합니다:

```bash
npx next dev -H 0.0.0.0
```

이후 다른 PC에서 `http://{개발PC_IP}:3000` 으로 접속할 수 있습니다.

### 11.2 환경변수 웹 UI 관리

환경변수는 웹 UI에서 직접 설정할 수 있습니다:

1. **보고서 상세** 화면으로 이동
2. **환경변수** 버튼 클릭
3. 키-값 형태로 환경변수 추가/수정/삭제
4. `.env` 파일 업로드를 통한 일괄 설정도 지원
5. 저장 시 해당 보고서가 자동으로 재빌드됨

> 기존 방식(서버에서 직접 `.env` 파일 편집)도 여전히 사용 가능합니다.

### 11.3 로컬에서 하위 경로(`/r/{id}`) 배포 환경 재현

보고서 자신의 API 호출은 로컬(루트 서빙)에서는 잘 되지만 배포(`/r/{id}` 서빙)에서만 어긋날 수 있습니다. 로컬 리버스 프록시로 `/r/test/` 형태를 만들어 배포 환경을 재현해 테스트하는 것을 권장합니다.
