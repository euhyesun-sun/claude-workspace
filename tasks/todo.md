### `UGM170-10002` 등 오래 offline인 차량의 API 응답 지연 — 근본 원인 확인 (수정은 보류)
- sun 요청으로 재현/조사 진행. `explain_chart.mjs`/`explain_tz.mjs`류 임시 조사 스크립트로 DB에 직접 접속해 단계별 `EXPLAIN (ANALYZE, BUFFERS)` 실행 (조사 후 전부 삭제, 코드베이스에 남기지 않음)
- **원인**: `/api/vehicle/chart`·`location`·`route-history`·`log` 네 API가 공통으로 쓰는 `resolveVehicleTimezoneHours()`(`src/lib/vehicleTimezone.ts`)의 쿼리 `SELECT timezone FROM bms_condition WHERE vehicle_id = $1 ORDER BY collect_datetime DESC LIMIT 1`가 문제
  - `bms_condition`의 인덱스 `idx_bms_condition`은 `(collect_datetime, vehicle_id)` 순서(시간이 선행 컬럼) — 그래서 이 쿼리는 테이블 전체에서 **가장 최근 시각부터 거꾸로 훑으면서** 지정한 `vehicle_id`와 일치하는 첫 행을 찾을 때까지 계속 진행하는 "Index Scan Backward" 방식으로 실행됨
  - `UGM170-10002`의 마지막 데이터는 8월 9일인데, 테이블 전체 최신 데이터(다른 활동 중인 차량들)는 8월 23일까지 있어서, 그 사이 14일 동안 다른 차량들이 쌓은 **약 624만 행**을 전부 훑고 지나가야 이 차량의 행을 찾을 수 있었음 — 이게 450초의 정체(실측: 단독으로 이 조회 쿼리만 실행해도 583ms~수백초, 테이블 크기가 커질수록 더 느려짐). 활동 중인(최근 데이터가 있는) 차량은 "최신"에서 몇 걸음 안 가서 바로 찾아지므로 빠르게 느껴졌던 것
  - `EXPLAIN`으로 확인한 실제 테이블 규모: `bms_condition` 전체 약 6,090만 행
- **중요**: 이건 "비교" 기능만의 문제가 아니라 이 헬퍼 함수를 쓰는 4개 API 전부에 공통된 문제라서, **오래 offline인 차량이면 어떤 화면(차량 상세정보, 로그 데이터 등)에서든** 이 지연을 겪을 수 있음
