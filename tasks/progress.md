### "경로만 보이고 최종/이전 위치는 안 보인다" — 진짜 원인 발견 및 수정
- 이전 턴의 "로딩 순서" 수정은 증상을 일부 완화했을 뿐, sun이 다시 재현("경로만 보이고 둘 다 안 보임")해서 근본 원인을 다시 팠음
- DB에 직접 psql 스타일로 접속해(node + pg 스크립트) 단계별로 검증한 결과:
  - `bms_condition.collect_datetime`은 timezone 정보가 없는 `timestamp` 컬럼
  - **node-postgres가 이 타입을 JS Date로 변환할 때 서버(호스트)의 로컬 타임존만큼 값을 빼버리는 동작**을 확인 (`to_char`로 원본 숫자를 직접 뽑아 JS Date 표시값과 대조해서 9시간 차이 확인)
  - 우리 API는 사용자 표시용으로 `collect_datetime + 9시간`을 계산해서 내려주는데, 이 값이 JSON으로 직렬화되는 과정에서 위 변환이 다시 9시간을 빼버려서, 브라우저가 실제로 받는 값은 결과적으로 **원본 collect_datetime과 숫자가 같음** (더하기/빼기가 상쇄됨)
  - 그런데 `/api/vehicle/detail`, `/api/vehicle/location`은 이 값을 넘겨받아 "원본으로 되돌리기 위해" **또 9시간을 뺐음** → 실제로는 이미 원본과 같은 값을 한 번 더 빼서 엉뚱한 9시간 전 구간을 검색 → 항상 데이터 없음(null) 반환
  - route-history/chart의 기간(period) 값은 브라우저에서 `datetime-local` 입력으로 직접 만든 값이라 이 문제가 없어서 경로만 정상적으로 보였던 것 — sun의 관찰("경로만 보임")이 정확한 단서였음
- 수정: 두 라우트에서 불필요한 "-9시간" 보정 제거, 받은 값을 `collect_datetime`과 직접 비교하도록 변경. 각 파일에 원인을 주석으로 남겨둠(다음에 비슷한 시간 관련 API 만들 때 같은 실수 반복 방지)
- 검증: 이전에 항상 비어있던 `ULM272-14033`으로 재확인 — 최종 위치 핀, 상세정보(작동모드/연료 등 실제 값), 차트 클릭 시 이전 위치 핀까지 전부 정상 동작. `npm run build` 통과, 콘솔 에러 없음
- **배운 점**: `timestamp without time zone` + node-postgres + 서버/DB 세션 타임존이 섞이면 "더했다 브라우저 갔다가 다시 빼면 상쇄된다" 같은 반직관적인 상황이 생길 수 있음 — 이후 시간 관련 쿼리를 새로 만들 때는 값을 그대로 눈으로 보고 판단하지 말고, `to_char`로 원본 숫자를 직접 확인하는 방식으로 검증할 것

### timezone 하드코딩 제거 (성능 수정 보완)
- sun 피드백: 지도 성능 수정 때 WHERE절에 `INTERVAL '9 hours'`를 상수로 박아넣었는데, 지금은 일본 서비스라 9지만 앞으로 다른 지역으로 확장되면 차량마다 timezone이 달라질 수 있어서 고정값은 위험하다는 지적
- 해결 방법 검토: row별 `timezone` 컬럼을 식에 직접 쓰면(원래 방식) 인덱스를 못 타는 게 문제의 핵심이었으므로, "컬럼 참조" 자체를 없애되 "고정값"도 아닌 제3의 방법이 필요했음
- `src/lib/vehicleTimezone.ts` 신규: 매 요청마다 `SELECT timezone FROM <table> WHERE vehicle_id = $1 ORDER BY collect_datetime DESC LIMIT 1`로 **해당 차량의 최신 timezone 값을 먼저 조회**(vehicle_id 인덱스라 빠름, 수 ms), 그 값을 메인 쿼리에 **SQL 파라미터로 바인딩**
- 핵심 원리: PostgreSQL은 바인딩된 파라미터 값은 쿼리 실행 내내 하나의 상수로 취급하므로(row마다 다시 읽는 컬럼 참조와 다름), `$2::timestamp - ($4 * INTERVAL '1 hour')`처럼 파라미터로 넘기면 인덱스를 그대로 쓸 수 있다 — 실제로 EXPLAIN ANALYZE로 재확인해서 인덱스 사용 유지되는 것 확인 후 적용
- `route-history`, `chart`, `log` 세 API 모두 이 방식으로 교체 (SELECT의 화면 표시용 계산은 원래부터 row별 timezone 그대로 사용 중이라 안 건드림)
- 브라우저 재검증: 여러 차량으로 지도(경로+핀)와 로그 데이터 화면 모두 정상 동작, 응답 속도도 이전 수정과 동일 수준(warm 상태 200~900ms) 유지 확인. `npm run build` 통과, 콘솔 에러 없음
- **배운 점**: 성능 최적화를 위해 실제 데이터에서 관측된 값을 그대로 고정값으로 박아넣는 건 위험할 수 있음 — "지금 항상 참인 값"과 "코드로 보장되는 값"은 다르므로, 가능하면 매 요청마다 실제 값을 조회해서 쓰되 그 조회 자체가 빠르도록(인덱스 타는 조회) 설계하는 방향이 안전

### timezone 9시간 지연 버그 + 공지 "최신 아님" 버그
- sun이 원본 사이트와 우리 사이트 스크린샷을 나란히 비교해서 제보: 같은 차량인데 데이터 시간이 9시간 차이 남, 중요 공지 내용도 다름

- 근본 원인: node-postgres가 timestamp(timezone 없는) 컬럼을 서버 로컬 타임존(이 환경은 KST)으로 해석해서 JS Date로 만들었다가, JSON 직렬화(toISOString) 시 다시 UTC로 바꾸는 과정에서 SQL이 미리 더해둔 +9시간이 상쇄됨 — 화면에 항상 9시간 느리게 표시되고 있었음. 로컬 `date`/`TZ` 확인으로 서버가 KST(UTC+9)인 것 확인, 임시 node 스크립트로 raw/shifted 값 직접 대조해서 재현 확인
- `db.ts`에 `types.setTypeParser`로 timestamp를 Date 변환 없이 문자열 그대로 반환하도록 수정 — 이 한 줄로 전체 화면의 시간 표시가 정상화됨
- 이 수정으로 인해 기존에 "round-trip 상쇄를 이용해 일부러 timezone을 안 빼던" `detail`/`location`/`alert-detail` 세 라우트는 로직이 깨지므로, route-history/chart/log와 동일하게 timezone을 다시 빼도록 되돌림 (grep으로 관련 코멘트 있는 파일 전부 찾아서 누락 없이 수정)

### 대시보드 위젯 — 마지막 행 잘림 + 위젯 간 행 수 불일치 수정

- 겸사겸사 `/vehicles`에서 이미 발견했던 것과 같은 sticky 헤더 버그(Tailwind 기본 `border-collapse`가 `position: sticky`를 막는 문제)가 이 두 위젯에도 있는 걸 확인해서 `border-separate border-spacing-0`으로 같이 고침(사용자가 요청한 건 아니지만, 같은 화면을 손보는 김에 같은 버그 패턴을 놓치지 않고 함께 정리)
- 빌드 통과, 브라우저에서 두 위젯 다 정확히 7행씩(잘린 행 없이) 나오는 것을 DOM 좌표 계산으로 직접 검증(각 행의 bounding rect가 컨테이너 안에 완전히 들어오는지 확인), 내부 스크롤 시 헤더 고정도 재확인

### 팝업 지도 — 위치 데이터 없음 안내 문구 + 숨어있던 (0,0) 버그
- sun 요청: 팝업 지도들 중 위/경도가 없어서 위치 표시를 못하는 경우엔 지도 위에 "차량의 위치 데이터가 없습니다."라고 표시

- 실제 데이터로 테스트할 "위치 없음" 케이스를 찾다가, 대부분의 차량이 실좌표를 갖고 있어서 못 찾다가 GNSS 통신 이상 계열 경고 메시지를 조사하던 중 진짜 버그를 발견함: `/api/vehicle/alert-detail`이 반환하는 `lat`/`lon`이 GNSS 미수신 시 `null`이 아니라 `0`으로 찍히는데(예: ULM272-14031, 2026-08-20 05:35:30 "GNSSとの通信で異常が発生しました" → lat=0, lon=0, quality="None", num_sv=0), `AlertDetailModal`의 위치 판정 로직이 `lat != null && lon != null`만 검사해서 이 (0,0)을 "유효한 위치"로 착각 — 실제로는 지도가 기니만(Null Island)에 마커를 찍고 있었음(사용자가 눈치채지 못했을 뿐인 기존 버그)
- 원래 `/api/vehicle/location`, `/api/vehicle/route-history` 두 API는 이미 SQL WHERE절에서 `lat <> 0 AND lon <> 0`으로 이 sentinel 값을 걸러내고 있었는데, `AlertDetailModal`만 그 기준이 빠져 있었던 것 — 같은 기준(`lat===0 && lon===0`이면 위치 없음 취급)을 `AlertDetailModal`의 `eventLocation` 계산에도 추가해서 통일
- 빌드 통과, 브라우저로 실제 GNSS 이상 경고(ULM272-14031)로 검증: 지도에 "차량의 위치 데이터가 없습니다." 정상 표시됨(더 이상 기니만에 마커 안 찍힘). 위치가 정상인 다른 경고(ULM272-14065)는 그대로 지도+마커가 잘 뜨는 것도 같이 확인해서 회귀 없음 확인

### 후속 발견 — "데이터 시간" 아래 상세 항목들도 안 맞던 진짜 버그
- sun이 날카롭게 후속 질문함: "데이터 시간 아래에, 작동모드, 시스템모드 데이터들은 그 시간에 값들 맞지?" — 확인해보니 실제로는 안 맞았음
- 원인: 방금 고친 건 "데이터 시간" 라벨의 표시값과 기간(period) 기본값뿐이었고, 정작 우측 정보 패널(작동 모드/시스템 모드/유닛 위치/남은 연료/속도/재생 데이터/진전/예상 종료 시간/경고 메시지)을 채우는 `/api/vehicle/detail` 호출과, 지도 최초 마커용 `/api/vehicle/location` 호출은 여전히 `referenceTime`(차량의 실제 최신 데이터 시간)을 그대로 쓰고 있었음 — 그래서 "데이터 시간"이라는 라벨과 기간은 경고 시점을 가리키는데, 바로 아래 값들은 차량의 "지금" 상태가 섞여 나오는 앞뒤가 안 맞는 상태였음
- `effectiveReferenceTime = periodReferenceTime ?? referenceTime`이라는 단일 변수로 통일해서, 상세정보 조회(`dataTime` 파라미터)와 최초 위치 조회(`at` 파라미터) 둘 다 이 값을 쓰도록 수정 — 이제 경고 목록에서 열면 데이터 시간 라벨/기간/작동 모드 등 정보 패널/지도 초기 위치까지 전부 하나의 시점(그 경고가 발생한 순간) 기준 스냅샷으로 일관되게 맞춰짐
- 검증 방법: 특정 경고(ULM272-12006, 2026-08-19 19:42:36)에 대해 `/api/vehicle/detail?dataTime=...`를 직접 호출해서 원본 값(작동모드 Service, 시스템모드 GNSS, 유닛위치 Down, 남은연료 30%, 속도 0.1km/h)을 먼저 확보한 뒤, 같은 경고로 실제 팝업을 열어서 화면에 표시된 값과 하나하나 대조 — 전부 정확히 일치하는 것 확인. 빌드 통과

### 온라인/오프라인 차량별 지도 갱신 로직 재점검 — 숨어있던 진짜 버그 발견
- sun이 큰 그림에서 다시 확인 요청: "대시보드/차량 상태의 online 차량의 경우에는 가장 최신 데이터를 보여주는게 맞고, offline 차량과 경고 목록의 차량 세부정보에서는 선택한 데이터 시간의 데이터를 보여주는게 맞아. 다시 확인해 줘" — 오늘 만든 `periodReferenceTime`이 이 네 가지 조합(대시보드/차량상태 온라인, 오프라인, 경고목록)을 다 올바르게 처리하는지 재검토하는 계기가 됨
- 코드를 다시 훑어보다가 `periodReferenceTime`과 무관하게 원래부터 있던 버그를 발견함: online 차량의 지도는 `REFRESH_INTERVAL_MS`(10초)마다 `/api/vehicle/location`을 다시 호출하고는 있었지만, `at` 파라미터로 넘기던 `referenceTime`(→ `effectiveReferenceTime`)이 컴포넌트가 마운트될 때 한 번 계산된 뒤 렌더링 내내 고정된 값이라, 10초마다 재요청은 하되 매번 "팝업을 처음 연 시각" 기준의 똑같은 ±1분 창을 반복 조회하고 있었음 — 즉 "10초마다 갱신"이라는 주석의 의도와 달리 실제로는 최신 위치를 따라가지 못하고 있었던 것(사용자가 계속 지켜보지 않는 한 눈치채기 어려운 버그)

- 빌드 통과, 브라우저 네트워크 요청 로그로 세 가지 조합을 전부 실측 검증:

- 수정: `VehicleMap`에 `resetKey`라는 문자열 prop을 추가해서, `FitBounds`가 이 값이 실제로 바뀔 때만(예: 보고 있는 차량이나 기간이 바뀌는 등 "완전히 다른 걸 보여줘야 하는" 시점) 화면을 다시 맞추도록 `useRef`로 이미 처리한 `resetKey`를 기억해뒀다가 같은 값이면 건너뛰게 함. 같은 `resetKey` 안에서 좌표 값만 갱신되는 경우(온라인 차량의 실시간 위치 갱신)는 지도 화면을 전혀 건드리지 않음
- 세 호출부 각각에 맥락에 맞는 `resetKey`를 넘김: `VehicleDetailModal`/`LogDataPanel`은 "차량ID-기간.start-기간.end", `AlertDetailModal`은 "차량ID-현재 보고 있는 경고 시각"(다른 경고 이력 항목을 클릭해서 다른 위치를 봐야 할 때는 그때만 새로 맞춰지도록)
- 빌드 통과, 브라우저로 직접 검증: online 차량 팝업을 열어 지도 확대(+ 버튼 3회 클릭) 후, 10초 간격으로 6회 이상 실시간 갱신이 일어나는 걸 네트워크 로그로 확인하면서(각 요청의 `at` 값이 계속 증가) 화면 배율이 리셋되지 않고 그대로 유지되는 것을 스크린샷으로 확인 — 마커는 차량이 실제로 이동해서 프레임 밖으로 나갔을 뿐, 확대 배율/화면 위치 자체는 전혀 안 바뀜

### 차량 상태 상세정보 팝업 — "차량 데이터"↔"로그 데이터" 전환 시 지도 재로딩 문제
- sun 질문: "아래 팝업에서 로그 데이터로 이동 / 차량 데이터로 이동할 때 지도를 새로 불러오는데 하나의 지도를 사용할 수 있을까?" — 대상은 대시보드/차량 상태에서 여는 offline 차량 상태 상세정보, 경고 화면에서 여는 차량 상세정보 둘 다(`VehicleDetailModal` 컴포넌트 하나를 공유)
- 원인 설명 후 진행 방식을 먼저 제안하고 sun 확인을 받음: "차량 데이터"/"로그 데이터" 두 화면이 `screen === "log" ? <LogDataPanel/> : <detail 화면/>`처럼 서로소 조건부 렌더링이라, 전환할 때마다 각자 안에 있는 `VehicleMap`(=Leaflet 지도 인스턴스)이 매번 통째로 사라졌다가 새로 생성되고 있었음
- 해결: 두 화면을 조건부로 "안 그리기"(unmount) 하는 대신 항상 DOM에 유지하고, 보이지 않는 쪽만 Tailwind `hidden` 클래스로 숨기는 방식으로 변경. `LogDataPanel`은 "로그 데이터로 이동"을 처음 누르는 순간에만 마운트하도록(`hasVisitedLog` state) 지연 마운트 처리해서, 애초에 로그 화면을 안 가본 세션에서는 불필요한 로그 데이터 조회가 안 생기게 함. 차량이 바뀌면(`trackedVehicleId` 로직) `hasVisitedLog`도 같이 리셋하고 `LogDataPanel`에 `key={vehicle.vehicle_id}`를 줘서, 차량을 바꿨을 때 이전 차량의 로그 데이터가 섞이지 않고 완전히 새로 마운트되도록 함
- 각 화면 내부의 데이터 재조회 로직(지도 위치/경로, 차트 등)은 손대지 않음 — 이미 `screen` 상태로 게이팅돼 있어서("차량 데이터" 화면의 지도 fetch effect는 `if (screen !== "detail") return`으로 시작) DOM이 항상 떠있어도 화면을 안 보고 있을 땐 불필요한 API 재호출이 안 생기는 게 원래도 보장돼 있었음
- 빌드 통과, 브라우저로 두 진입점 다 실제로 왔다갔다하며 검증: 최초 "로그 데이터로 이동"은 여전히 한 번 로딩되지만, 그 이후로는 "로그 데이터"↔"차량 데이터"를 몇 번을 왔다갔다해도 각 화면의 지도가 로딩 문구 없이 즉시 나타남. 검증을 더 확실히 하려고 두 화면에서 각각 지도를 다른 배율로 확대해두고 전환을 반복했는데, 매번 전환할 때마다 그 화면 고유의 확대 배율이 그대로 유지되는 것까지 스크린샷으로 확인(지도가 진짜로 재사용되고 있다는 증거)

### "기간" 변경이 지도까지 움직이던 문제 — 지도/차트 데이터 소스 분리
- sun이 스크린샷과 함께 요청: "기간을 선택했을 때, 위에 지도는 변경되지 않고 아래 차트에만 반영되게 수정해줘. 모든 화면." — 스크린샷은 `VehicleDetailModal`("차량 상태 상세정보" 팝업)이었지만 "모든 화면"이라고 명시해서, 같은 "기간 입력 + 지도 + 차트/데이터" 구조를 가진 다른 화면도 같이 점검함
- 점검 결과 같은 패턴을 쓰는 곳은 `LogDataPanel`("로그 데이터" 화면) 하나 더 있었음(지도의 이동 경로가 "기간" 값에 따라 자동으로 다시 그려지는 effect가 있었음) — `AlertDetailModal`은 애초에 기간 입력이 없고, `VehicleCompareModal`은 기간 입력은 있지만 지도가 없어서 이 문제 자체가 해당 안 됨
- 원인: 두 컴포넌트 다 지도용 경로 조회(`route-history`)와 차트/로그 데이터 조회가 같은 `period` state 하나를 그대로 같이 쓰고 있어서, 사용자가 "기간" 입력을 바꾸면 의도치 않게 지도까지 다시 그려지고 있었음(화면이 흔들리는 것처럼 보였을 것)
- 해결: 두 컴포넌트 각각에 `mapPeriod`라는 별도 state를 새로 추가 — 컴포넌트가 처음 열릴 때의 기간 값으로 딱 한 번만 초기화되고, 그 뒤로는 절대 갱신되지 않는 "고정된 지도 전용 기간"으로 씀. 지도의 경로 fetch와 `VehicleMap`에 넘기는 `resetKey`(확대/이동 상태를 언제 다시 맞출지 결정하는 값)는 이 `mapPeriod`를 쓰도록 바꾸고, 화면에 보이는 "기간" 입력과 차트/로그 조회는 기존 `period` state를 그대로 사용 — 결과적으로 사용자가 기간을 바꿔도 그 값은 차트/로그 조회에만 영향을 주고 지도는 처음 보여준 범위 그대로 유지됨
- 빌드 통과, 브라우저로 두 화면 다 검증:
  - `VehicleDetailModal`: 기간 시작일을 하루 전으로 바꾼 뒤 네트워크 로그로 확인 — `/api/vehicle/chart`는 새로 바뀐 기간으로 다시 요청되는데 `/api/vehicle/route-history`는 원래 기간 그대로 유지(추가 재요청 없음)
  - `LogDataPanel`: 지도를 미리 확대해둔 상태에서 기간 시작일을 바꿨는데, 지도의 확대 배율/위치가 전혀 안 바뀌는 것을 스크린샷 전후 비교로 확인

### "차량 데이터"→"로그 데이터" 이동 시 기간을 그대로 물려받아 데이터 없음으로 뜨던 버그 (online만 수정)
- sun이 스크린샷 두 장으로 제보: online 차량의 "차량 상태 상세정보"에서 기간을 "2026.08.20 오전 12:00~오전 02:59"로 좁혀둔 상태에서 "로그 데이터로 이동"을 눌렀더니, 로그 화면 지도에 "차량의 위치 데이터가 없습니다"가 뜸
- 원인: `LogDataPanel`은 `initialPeriod={period}` prop으로 부모("차량 데이터" 화면)의 현재 기간 값을 그대로 물려받아 자기 자신의 `period` state를 초기화하는데, 부모 화면에서 사용자가 임의로 좁혀둔 기간(위 예시처럼 새벽 12시~새벽 3시 근처의 3시간짜리 좁은 구간)을 그대로 물려받다 보니, 그 좁은 구간에 마침 해당 차량의 로그/위치 데이터가 하나도 없어서 "데이터 없음"으로 보였던 것
- sun 요청: "기간 객체를 차량 데이터 화면, 로그 데이터 화면 별도로 쓰게 해줘. online 화면만 수정해줘. (offline 기존대로 유지)" — 즉 두 화면의 기간을 완전히 독립시키되, online 차량에서만 이렇게 바꾸고 offline 차량은 지금처럼 부모 기간을 그대로 물려받는 동작을 유지해달라는 것
- `VehicleDetailModal.tsx`에서 `LogDataPanel`에 넘기는 `initialPeriod`를 `isOnline ? defaultPeriod(effectiveReferenceTime) : period`로 변경 — online 차량은 "차량 데이터" 화면에서 사용자가 무엇으로 바꿔놨든 상관없이, 항상 독립적으로 새로 계산한 기본 기간(그 차량 기준일의 00:00~23:59)을 씀. offline 차량은 이전과 완전히 동일하게 부모의 현재 `period`를 그대로 물려받음
- 빌드 통과, 브라우저로 실제 재현 시나리오 그대로 검증:
  - online 차량(ULM272-14064)에서 기간 끝을 "02:59"로 좁혀놓고 "로그 데이터로 이동" → 로그 데이터 화면의 기간 입력값이 좁혀둔 값을 무시하고 독립적으로 "00:00~23:59"(전체 하루)로 시작하는 것을 `input.value` 직접 비교로 확인, 실제 로그 데이터/미니차트도 정상적으로 값이 채워지는 것까지 확인
  - offline 차량(ULM272-14039)에서 기간 끝을 "03:15"로 좁혀놓고 "로그 데이터로 이동" → 로그 데이터 화면도 부모와 완전히 동일하게 "03:15"로 좁혀진 값을 그대로 물려받는 것을 확인(기존 동작 그대로 유지됨을 재확인)

### "기간이 지도에 영향 안 줌" 범위를 online 차량 데이터 화면 하나로 좁힘
- sun 요청: "online 차량의 차량 데이터에서만 기간 객체가 지도에 영향을 주지 않게 기존대로 유지하고, 다른 지도 객체들은 아래 기간에 따라서 조회되게 수정해줘" — 직전에 "모든 화면"(차량 데이터+로그 데이터, 온라인+오프라인)에 적용했던 "기간을 바꿔도 지도는 그대로" 동작을, online 차량의 "차량 데이터" 화면 하나로만 좁히고 나머지는 원래대로(기간을 따라 지도가 같이 바뀌는) 되돌려달라는 요청
- `VehicleDetailModal.tsx`: 지도 경로 조회에 쓰는 기간과 `VehicleMap`의 `resetKey`를 `isOnline ? mapPeriod : period`로 분기 처리 — online 차량은 고정된 `mapPeriod`를 계속 쓰고(직전 동작 유지), offline 차량은 사용자가 조정하는 `period`를 다시 직접 쓰도록 원복
- `LogDataPanel.tsx`: 직전에 추가했던 `mapPeriod` state와 관련 effect/`resetKey`를 전부 제거하고, 원래 코드처럼 지도 경로 조회가 `period`를 직접 쓰도록 완전히 원복(온라인/오프라인 구분 없이 이 화면은 항상 기간을 따라감)
- 검증 중 브라우저 자동화 도구가 한 번 300초 넘게 응답이 없어서(서버 로그상 dev 서버 자체는 "Compiling /" 이후 정상적으로 요청을 처리하고 있었음 — 브라우저 확장/CDP 쪽 일시적 문제로 판단) dev 서버를 완전히 재시작해서 해결, 실제 코드 문제는 아니었음
- 빌드 통과, 브라우저 네트워크 로그로 세 경우 전부 재확인:
  - online 차량의 "차량 데이터" 화면: 기간 시작일을 08-20→08-19로 바꿔도 `/api/vehicle/route-history` 요청은 계속 원래 날짜(08-20) 그대로 감 — 지도가 안 바뀌는 것 유지
  - offline 차량의 "차량 데이터" 화면: 기간을 08-20→08-19로 바꾸니 `route-history`가 즉시 새 날짜로 재요청됨 — 지도가 다시 기간을 따라가도록 원복된 것 확인
  - "로그 데이터" 화면(같은 offline 차량으로 이어서 테스트): 기간을 08-19→08-18로 더 좁히니 `route-history`가 그 즉시 새 날짜로 재요청됨 — 이 화면도 원복 확인

### offline 차량 — 기간에 데이터 없어도 "최종 위치" 마커가 계속 표시되던 버그
- sun이 스크린샷으로 제보: offline 차량(ULM272-14024)의 "차량 데이터" 화면에서 기간을 "2026.08.20 오전 12:00~오전 02:59"처럼 좁게 잡았는데, 그 구간엔 원래 데이터가 없을 텐데도 지도에 빨간 마커(최종 위치)가 계속 떠 있음. 바로 직전에 "offline 차량은 지도가 기간을 따라가게 해달라"고 요청해서 route-history를 기간에 맞춰 재조회하도록 고쳤는데, 그 후속으로 드러난 앞뒤 안 맞는 상태였음
- 원인 파악: 지도의 "경로"(파란 선, route-history)는 방금 고친 대로 정상적으로 "기간"을 따라가서 좁은 구간엔 데이터가 없으면 비어 있는데, "최종 위치" 마커(빨간 핀)는 별도의 `/api/vehicle/location?at=...` 호출로 채워지고 있었고 이 호출의 `at` 값이 여전히 `referenceTime`(이 차량의 실제 마지막 데이터 시간, "기간"과 완전히 무관한 고정값)이었음 — 그래서 경로선은 선택한 기간을 정직하게 반영하는데 마커만 항상 차량의 진짜 마지막 위치를 가리켜서, "이 기간에 데이터가 없다면서 왜 위치가 나오지"라는 모순이 생겼던 것
- 수정: offline 차량(online도 아니고 경고 목록에서 연 것도 아닌 경우)은 최종 위치용 별도 API 호출을 아예 하지 않고, 이미 "기간" 기준으로 불러온 `route-history` 응답 배열의 마지막 지점을 그대로 최종 위치로 사용하도록 변경 — `LogDataPanel`이 처음부터 쓰고 있던 것과 똑같은 방식으로 통일한 것. 이렇게 하면 그 기간에 경로 데이터가 하나도 없을 때 최종 위치도 자연스럽게 함께 사라져서(`null`), 이미 만들어둔 "차량의 위치 데이터가 없습니다" 안내 문구가 정확히 이 경우에 뜨게 됨. online 차량과 경고 목록에서 여는 경우는 원래 하던 대로 각자의 목적에 맞는 별도 조회를 그대로 유지(온라인은 "지금" 기준 실시간 추적, 경고 목록은 그 경고 시점 스냅샷)
